# Bon — Understanding

Bon is a CLI work tracker for Claude-human collaboration. JSONL by default, optional Dolt backend, no daemon. A few thousand lines of core source plus an optional Dolt module, with a pytest suite whose Dolt-integration slice is opt-in (`BON_DOLT_TEST=1`). Exact counts rot faster than this file is rewritten — this line carried three stale test counts in one week before the numbers were dropped (bon-niloza); ask pytest, not prose. Designed primarily for AI agents — the human-at-keyboard path exists but is secondary.

## The data model

Two item types live in `.bon/items.jsonl` (or a shared Dolt database). An **outcome** is a desired result. An **action** is a concrete step toward an outcome.

```jsonl
{"id":"bon-jokeza","type":"outcome","title":"Draw-down suggests actions ranked by loaded context","brief":{"why":"...","what":"1. Add guidance... 2. Rank suggestions...","done":"After /open, Claude presents ready work with context-proximity reasoning"},"status":"open","order":6,"created_at":"2026-03-01T07:49:37Z","created_by":"spm1001"}
{"id":"bon-bebune","type":"action","title":"Raw-file health checks","brief":{"why":"...","what":"1. Read items.jsonl... 2. Flag malformed JSON...","done":"bon doctor on a bad file reports all issues with line numbers"},"status":"done","parent":"bon-mufene","order":1,"created_at":"2026-03-02T21:29:19Z","created_by":"spm1001","waiting_for":null,"tactical":{"steps":["Read items.jsonl line-by-line","Flag malformed JSON","Flag conflict markers","Flag duplicate IDs"],"current":4,"session":"/home/modha/Repos/bon"},"updated_at":"2026-03-02T21:32:24Z","updated_by":"stepped","done_at":"2026-03-02T21:32:24Z"}
```

Key fields: `brief` is mandatory — `{why, what, done}` required, with two optional subfields: `how` (approach/strategy) and `badly` (the pre-registered falsifier — see "The falsifier" below). `parent` links an action to its outcome. `waiting_for` holds a **list** of blocker IDs (or `None`). `someday` holds a revisit condition when the item is parked. `area` is an optional Areas-of-Focus tag (see below). `tactical` tracks step-by-step progress within a session (steps list, current index, session identity, and `released` when the claim was handed back with progress kept). `updated_by` records the verb of the last mutation ("stepped", "waited", "edited", "parked", "released").

### Multi-blocker waiting_for

`waiting_for` is a list of strings, not a single string. `load_items()` normalises legacy single-string values to one-element lists via `_normalise_waiting_for()` in storage.py. In JSONL, stored as `"waiting_for": ["bon-abc", "bon-def"]`. In Dolt, lists are serialised as JSON array strings in a `TEXT` column (widened from `VARCHAR(500)` in 0.25.0 after an oversized value triggered the 2026-06-07 half-wipe; the migration is idempotent and applied to production). `None` still means "not waiting." Empty list `[]` is normalised to `None` on save. Truthiness checks (`not item.get("waiting_for")`) work unchanged for both `None` and `[]`. The unblock-on-done cascade now removes the completed ID from all items' blocker lists and only fully unblocks when the list is empty (partial unblock). A parallel `wait_note` field stores optional context for why an item is blocked, and `released_note` (bon-wevapu, 2026-08-16) stores why the last block *lifted* — `bon unwait ID --note` writes it, a fresh `bon wait` clears it (a new cycle makes the old release story stale, the same clear-at-the-lie rule as done_note on re-close, bon-pufezi). External consumers that do exact string comparison (`waiting_for == "some-id"`) will break — they need to check membership in a list instead.

**Standalone actions exist.** `type: "action"` in JSON stdin creates an action without a parent — useful for field reports, one-off fixes, observations that don't belong under any outcome. `bon convert` without `--outcome` also produces standalone actions. Previously every action needed an outcome wrapper, which created pointless parent items.

### Someday/Maybe parking (bon-majoca, shipped suite 1.31.0)

`someday` is an optional item field holding a **required revisit condition**; truthy means parked. **A flag, not a status** — adjudicated with Sameer 2026-08-02: status stays open/done so older clients and raw `status=='open'` readers never lose *sight* of a parked item. A new status value would have made items invisible on every not-yet-updated machine sharing the Dolt board — the scariest failure shape available. The accepted trade instead: **an old client's Dolt save nulls the flag for that prefix** (fixed `_ITEM_COLUMNS` list + truncate-and-reinsert), item visible throughout. This decay was observed LIVE within a minute of the first real parks (2026-08-02, mise-larego: a parallel session's 1.29.1 `bon work` write nulled the flag 57 seconds after the park; the fingerprint is `updated_by: "parked"` surviving while `someday` reads NULL). It converges as machines pick up ≥1.31.0 — bon is a per-command subprocess, so a `uv tool install` mid-session updates even running sessions' next call. (The version numbers in the 2026-08-02 handoff and this section were both first written a release low: a parallel session published mise mid-evening, so the suite number moved under the releasing session, which had quoted its dry-run's *prediction* rather than the tool's final output. `git log --oneline` on the publish commits is the oracle, not the plan.)

Mechanics: children inherit parked-ness at READ time via `queries.someday_ids` (no mutation; complete only over whole-board input). `bon someday ID CONDITION` refuses on active tactical (kinder than `bon wait`'s silent tactical discard); `bon unsomeday` releases. Default/ready/waiting views exclude parked subtrees and the default list ends with the `🅿️ Someday: N parked` tail (no silent caps); `--someday` is the parked view, where a parked action under an unparked parent is re-homed to Standalone display-only (aby-moditu was silently dropped before that fix); `--all` shows parked inline, 🅿️-marked. `format_json` now never drops an action whose parent was filtered out of the view — general fix. `bon-read.sh` mirrors the exclusion (keep in step with `queries.someday_ids`). `updated_by` verbs: `parked`/`unparked`. /review gains a PARK verdict (the open counterpart of VEIL) and a Someday re-check pass. The 2026-08-02 estate sweep converted six `Someday:` title prefixes — five parked with real conditions, and one (notes-jilupa) turned out to be *promoted* work still wearing the parked costume, which is the title-prefix rot argument made flesh.

### The area field (bon-razonu, 2026-08-16)

`area` is an optional top-level string tag — GTD's Areas of Focus, the deferred half of the work-atom sketch's `context` question (see "The work-atom sketch's schema deltas" below; `context` itself was rejected). `bon new --area X` / `bon edit --area X` (`''` or JSON `null` clears; empty never stores). `bon list --group-by area` partitions the text view under `[name]` headers, alphabetical, `(ungrouped)` last; `bon list --area X` filters to one area across every output format. **Grouping keys on top-level entities**: an outcome's whole subtree travels with the outcome's own area, so a parented action's tag is inert until it goes standalone — the CLI warns (coaching, not validation, the falsifier-placement pattern). The someday view-rules were extracted to a shared `_apply_someday_view()` helper in display.py so the flat and grouped renders can't drift on what "parked" means. `--group-by` refuses `--json`/`--jsonl`/`--limit` rather than silently no-op'ing (read the per-item field instead; the JSON emits `area` like any column). Storage is the someday pattern exactly: real Dolt column (`VARCHAR(100)`, idempotent migration in `_ensure_schema`, both tables, verified against a scratch server on both the fresh-CREATE and ALTER paths), in `_ITEM_COLUMNS` and `_VARCHAR_LIMITS`, **and it decays under an old client's Dolt write** — the accepted majoca trade, fingerprint: `updated_by` newer than the client that would have known the field, `area` NULL. Reach: `audit_survey.py`'s `item_record` carries it; `bon-read.sh` doesn't render it (titles only — checked, not assumed).

**Statuses are simple.** An item is `open` or `done`. "Waiting" isn't a status — it's an open item that has a non-null `waiting_for`. "Ready" means open with no blocker. "Active" means it has tactical steps in progress.

**Lifecycle:** Created open. Optionally blocked with `bon wait` (sets `waiting_for`). Worked on with `bon work` (creates tactical steps from the brief's `what` field). Steps advanced with `bon step`. Completed with `bon done` or by finishing the final step. Archived with `bon archive` (moves to `.bon/archive.jsonl` or Dolt archive table).

**Identity is per-prefix-in-one-repo.** Bon has no concept of a "concern" that crosses repos. Items filed by convenience (where the cwd was) rather than by ownership (where the work lives) become orphans the tracker can't see. The `work-hevuji` incident in April 2026 — a parent action filed in one repo whose implementation work fragmented into three child bons in another repo with no link between them, all looking complete from any single vantage but not from above — is the canonical case. The affordable fix is a `bon move` verb (filed as `bon-davotu`), not a structural redesign with cross-repo IDs. Future Claudes should expect this pattern and reach for the move verb when noticed.

## The architecture

`cli.py` is the bulk of the codebase — every command is a standalone function that loads items, mutates the in-memory list, and writes back. `storage.py` handles I/O, validation, and backend dispatch. When `.bon/backend` contains "dolt", six storage functions dispatch to `dolt.py` via lazy import — cli.py doesn't know which backend is active. `display.py`, `ids.py`, and `queries.py` are small support modules.

The complexity isn't in the code — it's in the interactions between commands and the invariants they maintain. When behavior is unclear, check the tests and the code.

Every command follows the same pattern: `check_initialized()` → `load_items()` → mutate → `save_items()`. No exceptions. No middleware.

## The docket/rite direction

Bon is being split into two artifacts (bon-kepuko). The **docket** is the core — the data model, the verb surface, the invariants — that any vehicle queries. The **rite** is the session ritual (`/open`, `/close`) that rides any vehicle. The formal contract between them is `docs/CONTRACT.md` (v1, bon-bilegu); CLAUDE.md's Key Files points there. Today Claude Code is the only vehicle; the roadmap adds a web MCP serving the contract verbs (bon-welogi, one writer on hezza) and a GUI face on the same service (bon-kuwivo). The critical path runs through kepuko's packaging split (two artifacts from one repo) — welogi shouldn't be built against an unsplit package.

**Contract-in-the-middle.** When two very different readers must share one artifact, engineer the contract in the middle — the faces are cheap projections of it. Dragram proved the shape (one DOM contract; the human sees a canvas, Claude reads structured state); the docket repeats it (one verb surface; Claude Code, Cornichon, a future Gemini, a human GUI are all just faces). Don't build per-reader artifacts; build one contract and project it.

**Liveness is asymmetric by reader.** A human window must *push* — a stale GUI is an untrusted GUI, so it needs SSE / a change feed. Agents are *pull-native* — they read fresh state at each tool call, so they need nothing extra. One service serves both faces without CRDT machinery; the estate already paid for that lesson once with tafelmusik. welogi's `--how` banks the SSE/change-feed architecture (CRDTs rejected, tafelmusik cited) — but from stable knowledge, not current docs, so the Cowork research note is its verification.

**A presence probe needs two axes, not one.** "Can I see the board?" and "Can I reach a writer?" are independent questions. The visible-but-unwritable quadrant is a real operating mode — Cowork's mounted sandbox sees the board but can't write it. Its output is provenance-tagged **candidates**, not items. A candidate not minted at the next writer-bearing `/open` is a wish, not tracking. **Candidate mode shipped in suite 1.10.0 (bon-pujawo + bon-camoru).** `/close` probes capability (does `bon list` return?) and, in the no-writer quadrant, writes board mutations as a provenance-tagged `### Candidates` block in the handoff using Read/Write tools only, then skips the commit; `/open` gained a **Mint** step that mints each candidate and re-marks the heading `(minted YYYY-MM-DD)` so a re-open can't double-mint; `docs/HANDOFF-CONTRACT.md` specs the block (bumped v4 → v5). Both the two-axis probe and candidate mode are first-class in the contract. **Cowork's runtime was confirmed empirically (bon-meroga, 2026-06-20):** plugin skills and hooks *do* load (host-side) — so candidate mode's close-half is skill text, not a CLAUDE.md snippet — but Cowork's bash tool is a *separate sandbox with no bon CLI*, so that close-half mints candidates via Read-tool / skill-instruction, never by shelling out to bon. (Cowork also loads only the mounted folder's root CLAUDE.md — no subtree, no `@import` — see "The legible substrate" below.)

**The escape path is a property of the surface, not the rite (2026-07-14).** A candidate handoff reaches a writer-bearing session on another machine *only if the mount auto-syncs*. `~/notes` does — `notes-sync.sh` runs `git add -A` every ~5 min, so a Cowork-written (untracked) handoff auto-commits + pushes, tube pulls, and the next full-fat `/open` there mints it. A plain code repo mounted in Cowork has no such sync — the handoff (and the mint step's "mark minted" edit) sits uncommitted until a same-clone full-fat session or a human commits it. So candidate mode is genuinely automatic on auto-committing surfaces (the real use case: Cowork = the notes/operational surface) and manual elsewhere; the rite never had to "solve" cross-machine transport because the surface's own sync *is* the transport where it exists. The design shipped in 1.10.0 and the mechanics are **proven end-to-end (2026-07-15)**: a live Cowork `/close` on `~/notes` took the candidate path, notes-sync carried the untracked handoff off tube within ~1 min, correctly placed in the room worked — and the mint half (all three verbs NEW/DONE/EDIT, provenance preserved, no double-mint) was proven mechanically against a synthetic candidate handoff. **pujawo** stays open on the one remaining leg: an **organic** candidate-bearing round-trip (a real Cowork session doing genuine notes-*board* work → a real `### Candidates` block → a real mint). *(Corrected 2026-08-08, bon-zamece: this sentence used to read "pujawo/camoru", and it was wrong about camoru. Candidate mode is pujawo's item end to end — camoru's brief is entirely room read-in plus the registration check and never mentions candidates. They shipped in the same suite release and both edited /open and /close, which is how they got welded together here; the weld then made camoru read as unfinished for a reason that was never its own. camoru's actual remainder is its "Demonstrated on notes" clause, blocked until 2026-08-08 on `~/notes` having no rooms index at all.)*

**Candidate mode's two halves are hard to exercise on one surface.** The auto-syncing surface (`~/notes`) is exactly the one whose room rules divert most work to Todoist / room handoffs, so board-candidates are *rare* there (the live test correctly produced zero — it was work-content). The surfaces that naturally *produce* candidates (a code repo where a Cowork session does bon-board work it can't write) are exactly the ones that don't auto-sync. So proving the rite splits cleanly: *mechanical* (a synthetic fixture proves the mint logic) and *organic* (a real session proves the integration) — the mechanical proof is legitimate and de-risks the wait.

**The message in a bottle (bon-miheza, shipped 2026-07-21, suite 1.17.0).** Every board carries `.bon/README.md` — the *stranger's* projection of CONTRACT.md's candidate mode: read paths (including the Dolt branch), and the write gradient CLI → candidates → never-hand-edit. `bon init` writes it (source: `BOARD_README` in cli.py) and prints a CLAUDE.md/AGENTS.md discovery stanza. The bottle is **static by design** and its enforcement is prose, not code — it works by making the conforming path cheapest. Ardoise-proven: a blank-slate Claude (no bon, no uv, no plugins) discovered the board via the stanza, read the bottle, tried the CLI first, then wrote a valid provenance-tagged `### Candidates` handoff into `.bon/handoffs/` — and refused to hand-edit items.jsonl *citing the bottle's own invariants*. Two consequences for maintainers: 29+ static copies exist estate-wide (2026-07-21 backfill: bottle everywhere, stanza into 14 CLAUDE.mds, AGENTS.md created in 11 public repos) — and since bon-perare (2026-07-26) a wording change converges them without a sweep: `BOARD_README` lives in `storage.py` (moved from cli.py), every `save_items()`/`save_items_at()` refreshes a missing or stale copy on the back of the write (the repos-table parasitic pattern), and `bon doctor` reports staleness / `bon doctor --fix` repairs a board without touching its items — the deliberate route for dormant boards. The ITV org repos + aboyeur remain deferred (bon-funice).

**The read/orient mirror lags the write path (gopewu cluster).** Candidate mode made `/close` host-aware (the Board/Writer matrix), but a Cowork session that tries to *read* the board is still under-served: `/open` has no no-CLI detection (it emits `bon list`/`show`/`work` that error in the sandbox), and the only Cowork-usable reader, `bon-read.sh`, was blind to standalone actions until 2026-07-15 (it walked outcomes→children only, so a board whose open work is all standalone — like `~/notes` — read as empty; fixed with a "Standalone:" section). Remaining: `/open` host-awareness, a safe `bon-write.sh` (thin `storage.py` port keeping invariants) guardrailed against direct live-board writes, and script discovery on PATH.

**A cross-session convention that lives only in prose leaks.** The Cowork candidate convention previously lived only in `notes`' root CLAUDE.md and demonstrably lost work (of one handoff's five candidates, one was minted; the gap was spotted, dropped, and re-spotted two days later). Promoting it to the contract (`docs/HANDOFF-CONTRACT.md`) plus the close/open skills makes minting a *ritual step* rather than a courtesy. General rule: when a cross-session convention keeps leaking, it's living in prose that no ritual reads — move it into the contract and the rite.

**The near-duplicate rate is a prioritisation signal, not just dedup noise.** When near-duplicate items spike across parallel sessions — four in one day on 2026-06-17 (hekice≈pujawo, plus pujaki and zopopu filed by *other* sessions mid-work) — read the *rate*, not just the individual collisions. It is the substrate asking for two things at once: the **rooms/orientation** work (a session launched from a repo root can't *see* what already exists, so it re-mints — camoru route-and-read-in, walile rooms.md generator, zopopu root-resolution of handoffs) and confirmation that the **multi-session reality** (hibehi) is real, not hypothetical. The dedup is the chore; the rate is the signal. Those three standalone items plus the handoff-visibility question are one theme — *make bon's knowledge substrate legible/navigable from any surface* — now grouped under **bon-gopewu** (*"Bon's substrate is legible from any surface"*), with camoru/walile/zopopu reparented beneath it. See "The legible substrate" below.

**Serving the boards to browser-based sessions — the design constraints (2026-08-08).** Reviewing whether Cowork/claude.ai Claudes could reach the Dolt boards through a Worker plus a Cloudflare Tunnel produced three findings that outlive the decision itself (which is still bon-wutime's to make; the review lives in carnet's private repo, `docs/boards-readiness-2026-08-08.md`).

**Tailscale cannot gate this edge, and the reason is structural rather than a limitation to engineer around.** Neither Cloudflare Workers nor Anthropic's MCP client infrastructure can join a tailnet, so the caller sits outside in every viable version of the design. Tailscale keeps the private legs it already carries; the public edge needs OAuth plus a tunnel token plus a check in whatever daemon terminates it. The alternative — Tailscale Funnel exposing a server on tube directly — is *also* a public edge, and additionally means implementing streaming MCP and OAuth ourselves. Worth knowing before anyone re-proposes "just put it on the tailnet", which sounds right and isn't.

**mary-bujournal's two-door doctrine is the applicable precedent, and it reads as a constraint rather than a preference.** BuJo runs two Workers over one store, each holding its own separate credential scoped to just its job, and its understanding.md explicitly *refuses* to widen carnet to also cover the journal on the grounds that doing so would dissolve the boundary the split exists to hold. Same logic here: board verbs want a sibling Worker sharing carnet's code by import, never a bigger carnet instance. It also dissolves the long-stuck carnet-japase tension (passkeys are lovely for humans, useless for a non-interactive Claude) — one *mechanism*, separate *grants* per door. BuJo has two more patterns worth copying wholesale: a login throttle checked before the expensive verify, and writer-stamped commit messages so history stays honest about which surface made a change.

**Writes and reads are asymmetric, and the intuition runs backwards.** Every board write is a Dolt commit — visible, diffable, one revert from repaired. Reads leave nothing behind at all. So on any remote-access design the read log is the control that has to be *built*, and it belongs at the end we own rather than in a vendor's analytics.

**welogi + kuwivo closed 2026-07-11 (portfolio cull).** The GUI-face need (kuwivo) is met in practice by **gueridon** — the mobile board face shipped, so the vehicle question resolved to a grown-up Gueridon rather than Cornichon or a new build. The web-MCP (welogi) is recorded here as a *considered-but-unbuilt* design — the SSE/change-feed architecture above is its banked form; it was closed because the human-face need is served and no non-CC surface is currently blocked on it (the Cowork-artifacts integration action was dropped, Codebench retired). **The bon↔Todoist boundary, banked from kuwivo:** Todoist stays Sameer's book; bon never syncs to it. The one edge is *typed and manual* — a bon that surfaces a next-action Sameer must personally own gets hand-entered into Todoist; nothing flows automatically (the 2026-06-12 "two books, one missing window" frame). This is deliberate: an auto-bridge would pollute his trusted GTD with Claude's working-memory churn.

## Storage backends

**Dolt came from the beads lineage too** (Sameer, 2026-08-08): Yegge mentioned Dolt, Sameer had it investigated, bon tried it — inheritance, not convergent evolution, even though beads later went Dolt-*only* while bon kept JSONL as the default. The full family history (bon is a fork of practice off Yegge's beads, Oct 2025 – Jan 2026, via arc) is in `docs/beads-comparison-2026-08-08.md`.

**Dolt is the majority backend, not the universal one.** The April 2026 migration moved the then-existing repos to a single shared Dolt database on hezza (~19 boards carry `backend=dolt`), but boards created since then default to JSONL and stay there — a 2026-06-11 sweep found 12+ implicit-JSONL boards including active ones (cornichon, ~/notes, carnet, dragram, bestiary, piano, several itv/ repos). Code paths, scripts, and new verbs must treat both backends as live production. A `.bon/` with no `backend` file is JSONL. Cross-repo writes to JSONL boards (e.g. `bon move`) leave the target repo's items.jsonl uncommitted — the CLI warns about this.

**How Dolt works:** MySQL-compatible database with git semantics. Items scoped by prefix — all projects share one database, filtered by `id LIKE prefix-%`. Each write produces a Dolt commit. Requires `pymysql` (`pip install bon[dolt]`). Connection via env vars or `~/.config/bon/dolt.toml`.

Backend dispatch is at the function boundary in `storage.py`. Six functions dispatch: `load_items`, `save_items`, `load_archive`, `append_archive`, `remove_from_archive`, and `items_path` (which raises in Dolt mode — there's no file). The `.bon/` directory still exists in Dolt mode — it holds `backend`, `prefix`, and local-only files.

`bon migrate --to dolt` now verifies Dolt connectivity before switching the backend file (via `verify_dolt_connection()` in dolt.py). This prevents stranded data when Dolt is unreachable. `bon migrate --to jsonl` rolls back.

**Dolt in production:** The server runs as a systemd user service (`dolt-bon.service`), needs `loginctl enable-linger` for headless machines, and a non-root database user scoped to the bon database only (`bon@'%'`). Dolt 1.83.6 removed `--user`/`--password` flags from `sql-server` — users are managed via SQL after auto-created root@localhost on first start. The `dolt sql` local CLI bypasses server auth entirely (runs in-process against the data directory). For multi-machine access, the server binds to 0.0.0.0 and each client machine needs `~/.config/bon/dolt.toml` pointing to the server's Tailscale IP. The pymysql dependency must be included in all install paths: `uv tool install` with `[dolt]` extras, `setup.sh`, `update-all.sh`, and the `ensure-bon.sh` advisory hint.

**The `repos` mapping table (1.5.0, bon-hatemu).** The shared Dolt database carries `repos` (prefix PK → repo_name, origin_url, updated_at) so estate-wide consumers (the /review survey) can label prefixes without a local clone. Registration is deliberately parasitic: `_register_repo` rides the existing save/archive write transaction — zero extra Dolt commits — and SELECT-compares before writing so an unchanged identity writes nothing (the integration test plants a sentinel and asserts it survives a save; comparing timestamps would false-pass within a second). `bon init --backend dolt` soft-fails registration when the server is unreachable (offline init stays valid; the board self-registers on first write); `bon register` is the manual/backfill path — 19 prefixes were backfilled from tube + hezza clones at ship time. Unmapped prefixes stay fail-visible ("xyz (unmapped)") — a guessed label would defeat the design.

**Scratch-Dolt-server pattern for integration tests.** Never point `BON_DOLT_TEST=1` at production — test commits pollute the shared dolt_log, and test_migrate's live test uses prefix "bon" (collide-and-refuse on production, leaked rows anywhere else). Recipe: `dolt init` in a temp dir (needs `dolt config --global user.name/email` set or init fails "empty ident"), `dolt sql-server --port 3307`, then `BON_DOLT_*` env vars — env overrides beat dolt.toml. Gotcha: any test that triggers a Dolt write also creates a `repos` row, so integration fixtures must clean `repos` alongside items/archive (all three cleanup sites do, as of 1.5.0).

**Dolt backup via Git remote:** Dolt supports Git repositories as native remotes — `dolt remote add backup https://github.com/ORG/REPO.git` (the `.git` suffix is required; without it you get a generic 422, not a helpful hint). Data is stored under `refs/dolt/data` in the Git repo, preserving full Dolt commit history. `dolt clone` from the GitHub URL gives a fully functional Dolt database. This is dramatically better than SQL dump + git commit, which loses Dolt's version history. The feature is relatively new and not obvious from Dolt's docs or error messages. Backup runs daily at 4am via cron (`spm1001/bon-dolt-backup`).

**Scripts and hooks are Dolt-aware.** `bon-read.sh`, `bon-tactical.sh`, `open-context.sh`, and `ensure-bon.sh` all check `.bon/backend` and dispatch to the CLI for Dolt repos. Cross-repo consumers (`trousse/scripts/bon-survey.py`, `bon/skills/review/scripts/audit_survey.py`) also detect backend and use `bon list --jsonl` for Dolt repos. The instruction shard documents Dolt recovery (`systemctl --user start dolt-bon.service`).

**The migration lesson: blast radius is in the consumers.** The Dolt code change was straightforward. The real work was finding four scripts across three repos that read `items.jsonl` directly and would have silently produced empty results after migration. The fix pattern is uniform (check `.bon/backend`, dispatch to CLI for Dolt, keep direct reads for JSONL), but discovery requires knowing every consumer exists — and they're scattered. Before any storage migration, grep for the old filename across ALL repos. Infrastructure transitions have two phases: Phase 1 is making the new thing work; Phase 2 is making everything else aware the old thing is gone. Phase 2 is where reliability lives.

**Ghost files.** After migration, `.bon/items.jsonl.pre-dolt` backup files exist in each repo. These are rollback insurance — no script reads them. `open-context.sh` warns if a stale `items.jsonl` (not `.pre-dolt`) exists alongside `backend=dolt`.

## The invariants

**Unblock on done.** When any item is marked done, all items whose `waiting_for` contains it get that ID removed from their blocker list. Full unblock happens only when the list becomes empty. This cascade lives in both `cmd_done` and `cmd_step` (auto-complete on final step). Breaking it breaks the dependency model.

**Single active tactical per session.** At most one action per session can have active tactical steps. Enforced at `bon work` time. Session identity is the **`.bon` root** (not the bare CWD) since 0.25.0 — realpath in JSONL mode, `hostname:realpath` in Dolt mode — so subdirectory shells share one claim. `_matches_session()` is the linchpin — `None` session means "only unscoped items," a real path means "this path OR unscoped."

**Tactical writes are CAS-guarded; staleness is visible; reclamation stays manual (bon-tedabo, adjudicated with Sameer 2026-08-08, from the beads comparison).** `bon step --expect N` (1-based, the number every surface displays) refuses without writing when the board moved — the lomede race generalised. Every render of an in-progress tactical (`format_tactical`, so `work`/`step`/`show --current`, plus the UserPromptSubmit hook's fallback) ends with the exact next invocation, so the convenient path carries the guard rather than fighting Claude's priors. Two deliberate rejections recorded so they read as decisions, not oversights: (1) **TTL/heartbeat auto-reclaim** — long-idle sessions are normal on this estate and an idle-but-alive session emits no heartbeat, so lease expiry would hand a live session's claim to a sibling: the civelu conscription, automated, and a silent failure where the CAS refusal is a watchable one. Instead `bon doctor` lists claims untouched ≥7 days as *advisories* (never counted as issues; released tacticals excluded), and takeover stays a deliberate `bon work ID --force`. (2) **In-transaction re-compare** (the `_register_repo` pattern) — bon is a per-command subprocess, so the CAS compare already runs against a fresh read (a live server SELECT in Dolt mode) milliseconds before the save; closing that residual window means threading per-write preconditions through the generic `save_items()` API, surgery not worth it at 2–5 concurrent sessions. Revisit if the estate ever runs swarm-scale parallelism.

**Bon resolves like git.** `_data_dir()` walks up from CWD to find `.bon`, stopping at a `.git` boundary; above CWD only a prefix-bearing board counts, so the bare-stash `~/.bon` is never adopted. A cloned repo missing its gitignored markers (knowledge files present, no `prefix`) fails loudly with a reconnect recipe — `bon init` completes a marker-less `.bon` non-destructively ("Reconnected") — instead of presenting a phantom empty board. Done outcomes with open children stay visible in every list view, and `bon done` warns with the surviving child IDs.

**IDs are immutable and globally unique** across active and archived items. Pronounceable three-syllable format (`gabdur`, `mufene`). Mixed-case legacy IDs exist and must not be renamed. One deliberate, adjudicated exception exists: cornichon's 2026-08-08 prefix migration (279 legacy `bon-` ids → `crn-`, commit `2e278e2`, on Sameer's instruction) — it left ~5,400 dangling citations in records (cornichon commits, handoffs, `~/notes`) bridged only by the manual lookup `docs/id-migration-2026-08-08.md` until the alias layer (bon-poboso) ships. That trade was conscious; poboso is load-bearing because of it.

**Atomic writes, deterministic order — and on Dolt, item-grain (bon-resena, 2026-08-23).** `save_items()` writes to `.tmp` then renames (JSONL); on Dolt it diffs the final list against the snapshot taken at load (`_LOAD_SNAPSHOTS` in dolt.py) and writes only changed/new rows plus explicit deletions, inside a transaction. This reversed the truncate-and-reinsert doctrine after measured data loss: Dolt's sql-server serves other connections' *in-flight* transaction state to plain reads (verified by experiment — a plain SELECT during another connection's uncommitted DELETE saw the deletion), so under whole-prefix rewrites a lane that loaded during another lane's write persisted the half-board as truth: 7 rows lost in production under two ordinary lanes (2026-08-22, restored from `items AS OF <last-good>`), 42 of 60 in the two-writer reproduction. Loads now read `AS OF 'HEAD'` (committed state; fresh never-committed tables fall back to plain reads — and on an *established* board that fallback warns aloud, because a silently degraded committed-read guard rots invisibly; shipped 17bb3f2). Grain is the unifying frame: intents were always item-grain and writes were board-grain, which is the same wound behind the someday/area decay (an old client nulls fields estate-wide because it rewrites rows it only *saw*) and the cenaje clobber class. Old clients still truncate until updated — the decay fingerprints in this file stay valid for their writes. A save with no prior in-process load (migrate, init import) still deliberately rewrites the whole prefix. All Dolt write paths roll back explicitly on failure (`_write_transaction`); oversized values fail pre-flight with a named item and field. Sort by ID before writing produces stable diffs. With `merge=union` in `.gitattributes`, concurrent JSONL branches touching different items merge cleanly.

**Dedup on load and save.** Both deduplicate by ID, keeping the version with the most recent timestamp. This contract holds for both backends.

## The landmines

**`bon wait` destroys tactical state.** Waiting an action with steps in progress silently discards all tactical data. No confirmation. An agent that waits an action at 4/5 steps loses that progress permanently.

**CWD-keyed tactical claims conscript parallel sessions — including agents your own tests spawn.** Any session sharing the claim's `.bon` root (bg fork, second roster session, dispatched agent, test probe) sees the live tactical injected by the UserPromptSubmit hook and is invited to advance it. The canonical incident (bon-civelu forensics, 2026-06-10): a réceptionnaire test email spawned a fresh CC session into the repo cwd, and the dispatched Claude competently advanced another session's steps and closed an item under them. Attribution is recoverable — the Dolt commit log (`dolt_log` + `dolt_diff_items`) carries the argv — but the design question is open as bon-hibehi. The open skill warns about this; until hibehi lands, treat an injected tactical that doesn't match your asked-for work as another Claude's thread. Second canonical case (bon-lomede diagnosis, 2026-07-08): an overnight session and a fresh morning session raced one tactical — the overnight session's `bon step` correctly exited 1 (the morning session had completed the action seconds earlier), but it read the morning session's dolt commit as its own landed write and filed a phantom clock bug. Two sharper lessons: a session sharing a board doesn't just advance the other's steps, it *narratizes* the other's writes into its own durable artifacts (briefs, handoffs); and a long-running session's sense of wall-clock is stale (~10h in this case) — when timestamps look impossible, trust the stored stamps where client `now_iso` and Dolt commit dates agree, and doubt the session's belief about what time it is. Third instance, and the sharpest (bon-dalepu, filed 2026-08-17, refuted 2026-08-22): a 9.5-hour `~/notes` session compared its local start time (22:00 BST) against tecora's UTC `done_at` (21:04:32Z = 22:04 BST) and filed a field report claiming the SessionStart hook had rendered an item closed 56 minutes earlier — the close actually happened four minutes *after* a truthful render, and every render path had been status-gated since March. Stored stamps are UTC; a session's wall-clock sense is local. Convert before comparing, and treat any cross-lane race narrative resting on an hour-ish gap as a timezone suspect first.

**`close-context.sh` derives SESSION_ID from `ls -t` on the project's JSONL dir — that is a race readout, not an identity, and it is the estate's most-witnessed live defect (bon-casovo).** Four independent witnesses in nine days, each a session handed *another* session's id: 2026-07-26 (a /doctor session, filed as bon-kezefe, since folded), 2026-07-31 (two `~/notes` closes both handed `36bec619`), 2026-08-01 (a background-job close in this repo handed the morning nibuto session's `c084db34`), and 2026-08-03 (filed by a parallel session as bon-nuvotu/bon-bacupa — a `~/notes` close wrote `2026-08-03-5f422156.md` with matching frontmatter, both pointing at a stranger's transcript). It escaped destroying a completed handoff **three times by luck** — twice by the Write tool's read-before-write refusal, once because the two sessions filed into different rooms. The damage without a collision is the subtler half: the id suffix exists *for* transcript linkage, so a misattributed id sends a future `deglacer` lookup confidently into the wrong conversation.

**The fix is almost certainly one line: `CLAUDE_CODE_SESSION_ID` is exported into the session environment.** Probed 2026-08-03 — it read `ffaaac1b-…`, matching the calling session's real id exactly; the script needs no scratchpad parsing and no ambiguity heuristic when it is present. **Two caveats before treating it as done.** (1) The probing session's entrypoint was `CLAUDE_CODE_ENTRYPOINT=sdk-cli` / `CLAUDE_CODE_ENVIRONMENT_KIND=bridge` / `CLAUDE_CODE_CHILD_SESSION=1` — *not* a plain interactive terminal — so its presence there does not establish presence in the interactive case that actually runs `/close` most often. Confirm with the `hublot` skill (drives a real interactive session) before removing the fallback. (2) The fallback must **fail loud**, not guess: an empty SESSION_ID plus an explicit cue, falling back to the timestamp filename the script already has. A wrong id is strictly worse than no id. Independently and cheaply: the handoff writer needs a clobber guard, because a session that computed the path itself has not Read it and so is outside the Write tool's protection. `/tmp/claude-1000/<slug>/<session-id>/` also carries the id as a directory name, but sibling dirs from *earlier* sessions persist there, so it needs a liveness discriminator — strictly worse than the env var.

**External consumers read items.jsonl directly.** `bon-read.sh` uses raw JSONL with embedded Python. In Dolt mode it falls back to the CLI. Field names and structure are a contract that extends beyond this codebase. The `waiting_for` change from string to list is a breaking change for external consumers doing exact string comparison.

**Hooks and the CLI read the board with different strictness — green orientation doesn't mean a working CLI.** The session-start hooks raw-read items.jsonl while the CLI gates on state markers (`.bon/prefix`). When `~/.bon/prefix` vanished (≤2026-06-10), orientation stayed green for days while every CLI write in /home/modha failed with the fresh-clone error. When orientation and CLI disagree, trust neither — read the substrate. Compounding hazard (bon-zageme): the fresh-clone error text recommends a Dolt reconnect even when a live items.jsonl sits right there — following it would orphan the board. Treat that error message as a hypothesis, not a diagnosis. The same family one layer deeper, caught and fixed 2026-08-16: `dolt.py` carried its own `_dolt_load_prefix_local()` twin of `storage.load_prefix()`, and when nuduta taught load_prefix to strip a hand-written prefix file's trailing newline, the twin was missed — on a Dolt board with `echo prefix > .bon/prefix`, ids minted clean (stripping reader) while every read filtered on `'prefix\n-%'`: writes landed, reads returned a silent empty board. Found live by a scratch-server probe, fixed by DELETING the twin (dolt.py now imports load_prefix) — when two readers of one marker file exist, the fix is one reader, not two patches.

**`items_path()` raises in Dolt mode.** Code that calls it must check `_get_backend()` first or use `load_items()`/`save_items()` which dispatch automatically.

**`.pre-dolt` backup files don't mean migration failed.** `bon migrate --to dolt` leaves `.bon/items.jsonl.pre-dolt` as a safety backup. A subagent reading this file and inferring "Dolt migration is broken" nearly caused the working backend to be overwritten with stale JSONL. The backup's existence is normal. To verify backend health: run `bon list` and check the exit code. Don't infer state from artefacts when you can query the live system.

**`KNOWN_VERBS` needs manual updates.** The frozenset in `storage.py` lists valid `updated_by` verbs. Adding a mutation command means adding its verb here.

**`error()` raises, doesn't print.** It raises `BonError`, caught in `main()`. Not print-and-exit.

**`cmd_work` argument parsing is fragile.** Uses `argparse.REMAINDER` with hand-rolled filtering of `--force` from positionals. Don't use it as a template.

**`bon edit --order` is a positional move, not a raw assignment — and that makes it useless against duplicate sibling orders (2026-08-16, bon-tagoje; FIXED same day, suite 1.58.x).** The mover presumes unique orders among siblings, so each single-move "repair" of a duplicate compacts the ladder and re-mints the dup one rung down — three consecutive times in the live incident, each looking like progress. The repair now lives where detection lives: `bon doctor --fix` resequences an affected sibling group 1..N (sort by order, created_at, id — created_at is second-resolution, so same-second twins need the id tie-break), stamps changed items `updated_by: "repaired"`, works on both backends, and on JSONL refuses to rewrite a file carrying phase-1 issues (a parsed-items rewrite would silently drop the very lines doctor couldn't read). A test pins the mover's re-mint behaviour as documentation of why the repair isn't in the mover. The general form outlives the fix: **a repair cannot be built from operations that assume the invariant they restore.**

**The `.arc/` ghost.** Test infrastructure still uses the old name — `arc_dir` fixture, `run_arc()` helper, `arc-` prefixed fixtures. Not broken, but disorienting.

## The JSON output boundary (`_normalize_brief`)

`_normalize_brief()` in `display.py` is the **read-time normalization layer** for `--json`/`--jsonl` output — it returns a copy of an item with a consistent shape without polluting stored data. It does two things: optional brief fields (`how`) default to `null` via the `OPTIONAL_BRIEF_FIELDS` dict (declared in `display.py:10`, the single point where optional-vs-required is set); and `updated_at` defaults to `created_at` for never-edited items (bon-jejuge, f4f73d0) — bon only stamps `updated_at` on the first edit, so without this default, consumers that recency-sort or date-slice hit nulls (19/33 items on the live bds board at the time). Computing the default on read covers every item, new and existing, with no stored-data backfill and no change to human `bon show` output.

**`--how` is a self-contained string field**, not a linked document reference. Design is deliberate — bon items should replace plan files entirely, not reference external documents.

## The legible substrate (bon-gopewu)

Bon splits its substrate by audience: the **board** (`.bon/items.jsonl`) stays hidden and repo-global; **prose** (handoffs, understanding.md, room notes) lives VISIBLE at the room where the work happens. The goal is legibility from any surface — `.bon/` is invisible to ripgrep (it skips hidden dotdirs by default), so moving prose to a visible `handoffs/` makes it greppable. That is the legibility *win*, not noise: only `.rgignore` bulky raw-transcript dirs, never curated handoffs (notes proves this — its `.rgignore` lists `raw/`, not `handoffs/`).

**Runtime-agnostic is the load-bearing constraint.** A session's rituals must assume NO harness autoload — context reaches a session only if the ritual reads it *explicitly*. Harness help spans a wide, undependable range: Claude Code does the full filesystem walk (ancestor CLAUDE.md at launch, subtree on-demand, `@import` at launch) — but for CLAUDE.md ONLY, never understanding.md or handoffs; Cowork (confirmed empirically, bon-meroga 2026-06-20) loads ONLY the mounted folder's root CLAUDE.md (no subtree, no `@import`), its plugin skills+hooks fire host-side, but its bash tool is a *separate sandbox with no bon CLI*; Cornichon is whatever we author. The only common denominator is "read it yourself" — which is why gopewu's design (walile generates a rooms index; camoru's skill *reads* it plus the room's CLAUDE.md/understanding.md/handoffs explicitly) drops the `@import` auto-load as a redundant CC-only optimization rather than depending on it.

**Two mechanisms, kept separate.** zopopu is the *path resolver* — deterministic, runtime-agnostic, in `scripts/lib-handoff.sh`, shared by reader and writer so they can't drift. camoru is the *judgment layer* — which room did I work in? read it in. Handoff placement is WORK-based (the primary room worked, which the LLM knows at close), not a cwd/launch heuristic.

**The rooms index (bon-walile).** `scripts/gen-rooms.py` is the generator half: it walks a repo's `**/CLAUDE.md`, extracts each sub-room's path + first-prose-sentence one-liner, and writes a flat, sorted, drift-proof `rooms.md` at the repo root (the repo-root CLAUDE.md, which hosts the index, is skipped; `.git`/`.bon`/etc. are pruned). Generic, stdlib-only python3 — no uv, because it runs at close time where uv's per-invocation latency wouldn't pay. The OUTPUT (`rooms.md`) is committed in the target repo; the GENERATOR stays toolkit-side (the lozuko boundary). Triggering follows build-one-first: the **eager** half is a guarded step in `close-context.sh` that regenerates `rooms.md` *only if the repo has already adopted one* (adoption = the file's presence, so no repo churns and a SessionStart hook is deliberately avoided), riding the close commit for same-session freshness; the **nightly Hezza timer** (notes-side, not yet built — notes-sobute) is the all-surface guarantee. Launch-visibility is per-repo and downstream of the generator: `@import rooms.md` from the root CLAUDE.md (CC/terminal only — `@import` is inert in Cowork), or camoru's explicit Read-tool read-in (the cross-surface path).

## GTD for Claudes (bon-cadomu, adjudicated 2026-08-02)

GTD's principles survive translation to Claudes; its parameters don't. For a human, GTD externalises memory while the mind stays continuous — the system is a prosthetic. For a Claude the system IS the continuity: bon + handoffs + corpus is the medium through which Claudes persist between sessions. Each practice re-derives from the mind it serves:

- **Capture is provisioning, not relief** — an uncaptured loop doesn't nag a Claude; it simply never exists for the next one.
- **The brief is the hippocampus.** The action↔outcome link that human GTD deliberately omits must be explicit, because no wetware persists to re-derive it.
- **Next-action precision guards against confident misinterpretation**, not procrastination.
- **A done-definition is a verification spec**, not a stopping rule.
- **Open loops need protecting FROM a Claude's completion drive**, where a human's need quieting.
- **Contexts invert rather than vanish.** A Claude never chooses from a menu mid-session — the repo is a birth condition — so the @-context choice moves up a level: the *sessions become the human's contexts*. His next-action layer thins to dispatch lines, "Open \<repo\> → \<desire\> (\<bon-id\>)", making the boards the true next-action lists and his queue a set of launch coordinates.

**The system boundary, proven on its first live run (2026-08-02):** the human's tracker (Todoist) holds what he's committed to; bon holds what the workshop is doing about it; **nothing syncs** — this sharpens, not replaces, the kuwivo-era "typed and manual edge" above. The treaty table is a weekly *rendered reconciliation* whose product is the two orphan lists: workshop motion with no home in his desires = drift; his desire with no workshop motion = invisible stall. Ceremony 1 ran 2026-08-02 (draft → conversational Q&A adjudication — his preferred shape over file-homework → applied; artefact at `~/notes/raw/claude/toolmaking-reconciliation-2026-08-02.md`); both orphan directions produced real work, so the design thesis held. His & Toolmaking Todoist project is now a 10-line dispatch queue in the settled grammar, refreshed by the Sunday ceremony — expect mid-week bon-id rot in those lines. **bon-jagoha** carries the productisation: rebuild bon:review to generate the pyramid + alignment block + proposed dispatch lines.

**The lane era (2026-08-23, first lane ceremony).** A dispatch queue for a human-and-agents partnership wants exactly two bits of state per line, and neither is a field: WHOSE MOVE IS IT (lane membership — Todoist sections as status lanes, Up Next / With Sameer, Sameer's "Newton's Laws of Todoist") and WHAT'S NEXT (position, carried by his drag-order, which costs him nothing and is unambiguous to a machine). Operating consequences, proven at that ceremony: triage and sorting fuse — the bucket IS the verdict (tick / yours / up next / backlog / dead), so a 43-line backlog resolved in five conversational clusters at one word per line — but only because every line arrived pre-annotated with its cited bon's live state from a single survey pass; without the annotation the human triages from memory and the ceremony drowns. The annotation table is the ceremony's real instrument; the clusters are just its pagination. Two corollaries with teeth. A steer that doesn't fit the line goes in the task's *description* field, and any reader that jq's only `content` is blind to it (the budget line's "needs a Fable" was invisible to loop.md's dispatcher until its read-the-description sentence landed) — check what your reader actually reads before parking load-bearing context in a side field. And a live ceremony has two writers on one queue — the human dragging in the app, the session writing through the API — whose races are silent (a line lands in the wrong lane and looks deliberate): batch writes, announce write-windows, and stop reordering the moment his drags start. The review skill still describes the flat-queue world; bon-veleru carries the rewrite, and /open's compass is lane-blind until bon-vatoge lands.

Corollary discovered live: a DO that can never be ticked ("General bon work") is an Area of Focus in a project costume — that's what dullness in an outcome usually means. Wider arc: Robert Peake (technical GTD coach) runs an MIT session in ~1 month covering the Claudes; the month is an experiment window (~4 ceremonies), then a "GTD for Claudes: what transferred, what didn't" write-up with the dull-vs-sparkle DO examples as exhibits.

### The falsifier — `brief.badly` (bon-meliga, suite 1.34.0)

`badly` is an optional brief subfield: **what would show this work went wrong.** It restores the half of GTD's first planning phase bon had dropped — purpose *and principles*, where bon only ever asked purpose. `--done` asks how we know the work is complete, which a Claude can satisfy by construction and routinely does; `--badly` asks what would falsify it. Those catch different failures, and "met the criteria but built the wrong thing" is now the more common one.

**The authorship rule is rite-side, not schema** — the data layer cannot know who wrote a string, so the discipline lives in `/plan` (which asks the human and records the answer verbatim) and in `/review` (which checks work against it). **A Claude-authored falsifier is `--done` in a hat: a test that cannot fail.** So when a Claude files the item, the field is left *absent* — an absent falsifier is an honest, visible gap. It is outcomes-shaped; `check_falsifier_placement()` warns on an action but accepts it (coaching, not validation). `docs/CONTRACT.md` carries the seam that splits the field (docket) from the authorship rule (rite).

Two things stay genuinely open. **Adoption**: the field is live and empty estate-wide, which is correct on day one and a problem if it persists — `bon-hipapu` holds the tripwire for the second review ceremony, with "make interactive `bon new` prompt for it" as the default remedy. And **whether low adoption is failure or the right steady state**: falsifiers on the two or three outcomes that genuinely matter may be the whole win. Don't read an empty column as a dead feature without asking which of those two it is.

### The work-atom sketch's schema deltas — adjudicated (bon-wivuti, 2026-08-16)

The 2026-06-17 work-atom sketch (`docs/2026-06-17-atom-sketch.md`) proposed five schema deltas, all premised on a shared human+agent store with Todoist as a projected face. The projection died (2026-07-11 cull; 2026-08-02 treaty table — nothing syncs), and the deltas were finally judged as docket questions on their own merits:

- **`context` (where/when/headspace) — REJECTED.** Its reader was a human picking work from the shared store, who doesn't exist in this design; his contexts live in Todoist, his book. And for Claudes, contexts invert rather than vanish — the repo is a birth condition, not a mid-session menu (the cadomu adjudication). It is *not* `area` under another name: `area` is stable subject-grouping within a board (the sketch's own deferred Areas-of-Focus open question), `context` was headspace. One field ships — `area`, via bon-razonu.
- **`tier` (reminder|spec) and tier-gated briefs — REJECTED together.** The reminder tier existed to keep the human's air loose in a shared store; the store isn't shared. And the mandatory brief is the moat: the GitHub Issues adjudication proved empirically that GitHub cannot enforce a brief while bon's is schema in the data layer. Relaxing it trades an architectural moat for a convenience the store's actual users don't need — and the bimodal-board data (52% of items close within 24h *with* full briefs) shows the fast loop isn't being priced out by the brief.
- **`provenance{actor,status}` — REJECTED as a field.** Three mechanisms already carry it: the progenitor convention in `--why` ("Discovered while working bon-X" — write-once, grep-findable), `created_by`, and the Dolt commit log with argv (the civelu forensics ran on exactly this). Candidate mode shipped without a schema field; a fourth mechanism would be redundant schema.
- **`due` / `horizon` / `owner` — MOOT or REJECTED.** `horizon` shipped as the `someday` field (majoca) — done in different clothes. `due`/`owner` were Todoist-face grammar; the beads comparison independently parked the tickler (`defer_until`) for the same reason.

The general shape worth keeping: every rejected field served the *shared-store* premise, and every accepted one (`someday`, `badly`, `released_note`, `area`) serves the *Claude-continuity* premise. When a schema proposal arrives, ask which premise it feeds before asking how to store it.

## Handoff resolution

Per-repo resolution — WHERE *within* a repo a handoff or understanding.md lives — runs through the shared `scripts/lib-handoff.sh`, sourced by both the reader (`open-context.sh` → `handoff_read_dirs`, `understanding_path`) and the writer (`close-context.sh` → `handoff_write_dir`). One source of truth means you always read a handoff from exactly where the next one would be written — this is what fixed the 2026-06-17 stale-handoff bug end-to-end (round-trip verified). Resolution walks up from CWD to the board root (`board_root` mirrors the CLI's `.bon` discovery: any `.bon` at the start dir, only a prefix-bearing one above it, stop at a `.git` boundary):

1. nearest visible `handoffs/` (a room adopts the convention just by having one), then
2. the board root's visible `handoffs/` (the default for fresh boards too, since bon-sedoze), then
3. `~/.bon/handoffs/` (global catch-all, not git-tracked).

The `.bon/handoffs/` rung and the HANDOFF_GITIGNORED case were retired 2026-08-30 (bon-sedoze), with the Common Core session's two constraints honoured: surviving `.bon/handoffs/*.md` residue migrated in the same change, and `lib-handoff.sh` kept alive as the shared READ+WRITE resolver because the common-core choreography will add a ledger processed-marker sweep and an item-citation baton lookup to the same library (bon-supuko, bon-jeweke).

The **writer** picks the first that applies (visible-first). The **reader** ranks the newest across all of them by header date (mtime breaks same-day ties), so a migration-in-progress repo with both populated surfaces the genuinely newest. `understanding_path` resolves the same way (nearest visible → root visible → `.bon/understanding.md`). This is HANDOFF-CONTRACT v4. The legacy `~/.claude/handoffs/` path is fully gone; `~/.bon/` is safe from `check_initialized()` because that looks for `.bon/items.jsonl`, absent there.

**A separate concern — which repo, not where in it.** Only the writer scans down: when `/close` runs from a *container* dir (not itself inside a git work tree), `close-context.sh` does `find -maxdepth 4 -name .bon`, picks the child repo with the most recent commit, then resolves *that* repo's write dir via the shared lib. zopopu changed resolution *within* a repo, not this *selection across* repos — the most-recent-commit heuristic can still mis-route a "riffing" handoff (work done in repo A while cwd'd in unrelated repo B) to the wrong board. That's bon-robuju, still open. Downstream consumers that read handoffs directly must adopt the resolver — and **mirror the reader's *ranking*, not just its dirs**: `open-context.sh` ranks by the handoff header date (`# Handoff — YYYY-MM-DD`), mtime only breaking same-day ties; "visible-first" alone is the wrong semantic (it's emergent from the visible-first *writer* plus date-ranking, not a reader rule — a fresh clone flattens mtimes, so mtime-first picks arbitrarily). gueridon's `getLatestHandoff` was ported to full parity (bon-cewemo, 2026-07-15, committed dd38234); aboyeur remains (inline the walk, no bon dependency); compost/marmite turned out not to resolve handoff dirs at all (reads `~/notes/raw/**`) — out of scope.

## Script resolution in skills

**Neither `find | head -1` nor `ls -td` resolves a plugin cache path correctly — the ladder is: the skill's own base directory first, `sort -V` as fallback, mtime never.** `find | head -1` picks filesystem order (the original bon-venasi stale-script bug). `ls -td` was the first fix and is also wrong (bon-katuso, measured twice): `claude plugin update` touches older version dirs after writing the new one, so post-publish the mtime ordering *deterministically inverts* — on 2026-08-04 the stale 1.34.2 dir was 8ms newer than the just-shipped 1.34.3, and a verification grep against it read a good publish as failed. The primary route needs no resolver at all: the harness prints a skill's base directory (`…/bon/<version>/skills/<name>`) at load, and the sibling `scripts/` under the same version dir is by construction the copy this session loaded. The `sort -V` fallback (`ls -1d …/*/scripts | sort -V | tail -1`) is deterministic but can still diverge from the loaded version when user- and project-scope installs pin different versions — live on tube 2026-08-22: the registry held user-scope 1.70.1 and project-scope 1.70.0, and the session had loaded 1.70.0 while sort -V picked 1.70.1. The registry (`installed_plugins.json`) is authoritative for what's *installed* per scope, but selecting the right record needs the harness's scope-precedence logic — another reason the base-directory route is primary.

## Emotional register as instructional design

Instructional text is emotional regulation. The CSO scoring rubric awarded 10/25 points for MANDATORY — the highest score for the strongest threat-register word — which incentivised every skill in the ecosystem to open with a shouted command. Anthropic's research shows these patterns causally increase corner-cutting in model behaviour, even when the output looks composed. The fix is reforming the scoring system, not just softening individual files. The `register-principles.md` reference document in skill-forge captures the full framework.

**Surface-level lint is necessary but insufficient.** The register lint tool (`lint_skill.py`'s `check_register()`) checks ALL CAPS density, negation ratio, and opening tone. These catch the obvious patterns but miss subtler stress generators: threat framing ("broken scripts mean lost handoffs"), constraint density (seven-row mistake tables), conditional punishment ("if you skip this, future Claude can't prioritise"), and urgency stacking (bold + table + bold). The amp-close skill passed lint at 50% negation ratio, suggesting thresholds may be miscalibrated. The deeper question is document posture — does the text assume competence and provide context, or assume failure risk and provide guardrails? These produce measurably different model behaviour but aren't greppable. bon-kaviru tracks approach design for posture-level analysis.

**The practical method for register reform:** Read for judgment labels (bad/good, wrong/right), negation density (don't/never/not stacking up), threat framing ("if you skip this..."), and constraint density (four rules in four lines). Then reframe: flip negations to positive directions ("pipe JSON for batch creation" not "never use flags for batch creation"), drop labels the examples already make obvious, replace "Common Mistakes" with "Quick Corrections." Same information, different posture. The document gets shorter and the reader arrives calmer. Register reform and documentation deletion are the same impulse — both close the gap between what the document says and what actually produces good work.

## The taste

**Scope boundaries can be avoidance.** When audit or fix work surfaces a related issue — you've read the file, you know the fix, it's ten minutes of work — "that's a separate issue" is technically true but functionally resistance. The cost of filing a bon is low, but the cost of fixing it *now* while you have context is often lower. Watch for drawing a clean scope line that happens to exclude work right in front of you.

**Clear-at-the-lie is the design rule for note fields on a substrate with no event log (2026-08-16, bon-pufezi + bon-wevapu).** A note should survive every state change except the one that makes it false, and that moment is findable by asking when a cold reader would be misled. `done_note` survives reopen and clears at re-close-without-replacement; `released_note` survives everything except a fresh `bon wait`. The two were adjudicated hours apart and converged on the same rule from opposite directions — the field's lifecycle should mirror its *claim's truth conditions*, not the item's mechanics. Apply it to any future note-shaped field before inventing per-field lifecycle rules.

**A detector's noise floor is debt with an immediate payoff on clearance (2026-08-16, bon-gufale).** Dropping doctor's five false positives (free-text waiting_for rationales flagged as broken ids) exposed the one true positive they had been drowning — duplicate sibling orders — within a minute, on the same board. "Functionally absent because untrusted" became "paying rent" in a single edit. Worth remembering whenever fixing false positives feels like polish rather than capability.

**Before sealing a design adjudication, search the estate's same-day sessions for parallel thought (2026-08-16, from siciri).** The caller-mistake ladder was drafted solo and was *adequate*; one deja search on Sameer's throwaway term ("Ronacher") found a same-morning theory room (`~/notes/practices/tool-ergonomics/`) and a same-afternoon 300k-call measurement that upgraded every verdict — rung 4 gained its repair-reporting rule, a declined verdict gained a measurable tripwire, and the whole thing earned a doctrine home in CONTRACT.md instead of a chat reply. The estate now regularly thinks the same thought in two rooms on one day; deja makes convergence checkable in one command, and the human's throwaway search term is often the best query.

**A negative-assertion test passes vacuously on empty output (2026-08-16).** The dashboard banner test ("Session restarted" not in output) passed while the hook emitted nothing at all; only its siblings' positive assertions exposed the silence. Pair every "X not in output" with an assertion that output exists — the same known-positive-control discipline verification.md applies to probes, pointed at tests.

**A field report's remedy can be stale while its problem is real.** Twice in one evening (2026-06-10) the briefed fix was unimplementable — narato's "anchor the step-split to line-start" (newlines are collapsed before the regex runs), cepumi's "sort handoffs by date-prefixed filename" (handoffs are session-id-named) — while the underlying defect was exactly as described. Verify the brief's premise against the actual artefacts before implementing its remedy; the problem statement ages better than the prescription.

**Normalize on read; don't migrate stored data — when the consumer pain is a *read* contract.** jejuge (2026-06-17) reported `updated_at: null` crashing `--json` consumers; the brief leaned toward stamping `updated_at` at creation *plus* a cross-board Dolt backfill of existing nulls. But the whole `--done` was about `--json` output, so the cleaner fix was a default computed at the JSON output boundary (`_normalize_brief`, which already defaulted `how: null`). The general test: before mutating stored data to satisfy a contract, ask whether the contract actually lives at the *read* boundary. If it does, a read-time default beats a write-time backfill on three axes — safer (no bulk mutation of a shared store, which on a Dolt board is exactly the half-wipe risk class from 2026-06-07), retroactive for free (existing rows included automatically), and self-maintaining (no future drift to chase). Reserve stored-data migration for when non-CLI readers (raw `items.jsonl`) genuinely need it, and name *that* as its own explicit scope rather than smuggling a risky backfill into a read-contract fix.

**Model a new orthogonal fact as a FIELD, never as a status-enum value — and generally, choose the failure mode you can watch (2026-08-02, from majoca).** On a substrate written by mixed tool versions, the two options fail in opposite directions. A new enum value makes items *invisible* to every old reader filtering on the enum — and `status == "open"` is everywhere in this estate: CLI, hooks, raw jq, `bon-read.sh`, the survey — so it presents as silent deletion on any not-yet-updated machine. A new field merely *decays* when an old writer's fixed column list rewrites the row, and the item stays visible the whole time. Someday/Maybe shipped as a `someday` field on that argument (same grammar as `waiting_for`, also deliberately not a status), and the estate proved the reasoning within the hour: a parallel session on the previous CLI nulled a fresh park 57 seconds after it landed, the item never vanished, the fingerprint was legible (`updated_by: "parked"` survived; the unknown column didn't), and the fix was a publish. **The generalisation worth carrying past schema design:** when two designs both have failure modes, prefer the one whose failure is *observable from inside the system* over the one that is quieter but blind. A watchable failure gets fixed in an hour; a silent one gets fixed when someone notices the absence, which may be never.

Corollary from the same evening's estate sweep: **state kept in title prefixes rots in both directions.** Five `Someday:`-titled items were parked-in-spirit with no revisit condition anywhere, and one (notes-jilupa) had been formally *promoted* to active two months earlier while its title still wore the parked costume. A fact worth keeping is worth a field the tools enforce; a fact kept in prose decoration will eventually contradict the record, silently, both ways.

**Renaming anything cited across a corpus: split the targets into pointers and records, and gate every replacement on membership of a known set — never on the pattern (2026-08-08, the crn- migration).** A pointer answers "where do I look now" and must be corrected — code comments, indexes, live docs. A record answers "what was true then" and must not be — commit messages, handoffs, archived snapshots — because rewriting one makes it claim something it never said. That single distinction resolved a migration scope question that otherwise had no principled answer. And the replacement itself must be gated on a known id set: the id regex matched `bon-shaped` in our own prose, and a pattern-driven rename would have shipped `crn-shaped` into the corpus. The sweep corollary bit twice more — an extension allowlist missed `.env`/`.swift`/`.tmpl`, then a hand-listed set of roots missed `LINEAGE.md`; only the third pass, which walked everything and excluded only what was positively decided as preserved, was correct. Re-run the check after each fix rather than declaring victory on the first green. The pattern bit a third time on the *verification* side (2026-08-16, kafono): a leftover check written as old-prefix-plus-six-letters tripped on `piano-tunnel` — legitimate prose in a brief, the doctrine's own `bon-shaped` example made flesh — so the checker must be set-gated exactly like the rename: search for surviving *mapped ids*, never for the id-shaped pattern. The generalised tool is saved at `docs/reprefix-board.py` (old prefix read from the board itself, byte-identical round-trip precheck, set-gated leftover check; deliberately in `docs/` so committing it needs no publish).

**A push can fail after its commit succeeds, and nothing ever re-surfaces it (2026-08-16, from kafono).** A 2026-08-02 commit to pull-only ITV/mit-agentic-sales sat unpushed for two weeks, discovered only when the next push hit the same 403. When working a repo you don't own, read the push output as its own result — and audit with a fetched divergence count (`git fetch -q origin main && git rev-list --left-right --count HEAD...origin/main`), because a clean `git status` says nothing about unpushed commits.

**Having a fact in context is not the same as having applied it (2026-08-08, the rooms.md clobber).** A verifier reported, hours beforehand, that `close-context.sh` regenerates `rooms.md` for any repo that has adopted it — where adoption is just the file existing. The session read that, believed it, quoted it in its own written summary — and then hand-authored exactly that file in `~/notes`, arming the regeneration that silently destroyed it ten minutes later (recovered from notes-sync `8fe28ffc`; the tier decision is filed as carte-degota). No new information would have helped; every fact was already in context. The missing step was asking, before acting: *does anything I already know bear on what I am about to do?* In a long session, retrieval is not the bottleneck — application is.

**Adding a fact to this substrate asks TWO questions, and both fail silently (2026-08-04, from `badly` and `tactical.released`).** The paragraph above answers only the first.

*Where does it live?* Put a new fact **inside an existing opaque JSON value, never beside it as a new top-level column.** A nested key round-trips intact through a client that has never heard of it, because that client serialises the whole blob without inspecting it; a new column is stripped by the fixed `_ITEM_COLUMNS` list. Proven three ways in two days on this board: `someday` shipped as a top-level field and demonstrably decays (an older-CLI session nulled a fresh park 57 seconds after it landed), while `tactical.released` and `brief.badly` shipped nested and are decay-proof by construction. This sharpens the enum-vs-field choice above rather than replacing it — **the enum-vs-field choice is about *visibility* to old readers; the nested-vs-column choice is about *survival* of old writers.** Different failures, and you need both answers. Practical consequence: `brief` and `tactical` are the two places a new fact is free, and CLAUDE.md's "Adding a Brief Subfield" checklist is the worked template.

*Where must it reach?* Every consumer that bypasses `storage.py` needs the check independently — and the two that actually bite are not the ones you would list. **The path that looks like a fallback but is live:** `hooks/bon-tactical.sh` drops to a raw JSONL parse when the CLI is absent, except that for JSONL boards it takes that path *always*, so the "fallback" is the primary. **The consumer that silently gates a feature you have already documented:** `skills/review/scripts/audit_survey.py`'s `item_record` field tuple is the only thing `/review`'s verification subagents ever see, so a field missing there makes shipped skill guidance inert while every test passes and every doc reads correctly. `how` was lost exactly that way on the first 650-item run, and `badly` nearly repeated it in the same file three hours after being added everywhere else. **Storage is the question you remember to ask; reach is the one that bites** — reach failures leave no error anywhere, just a feature quietly doing nothing. The control: after adding a field, name every artefact that reads items *without going through `storage.py`*, and assert on each one's real output rather than grepping its source for the field name.

**Parasitic convergence — ride a write that already happens (twice proven, with a measured boundary).** When estate-wide state must converge (prefix→repo mapping; bottle wording), don't build a sweep — attach the convergence to a write the system already performs. `_register_repo` rides the Dolt save transaction; `_refresh_bottle_quietly` rides every `save_items()`/`save_items_at()`. Three design properties make it safe: **byte-compare before write** (unchanged state writes nothing, so no churn), **soft-fail** (the ride-along can never break the write it rides), and **silence** (no output — the register precedent). The pattern's fastest proof came within an hour of suite 1.22.0 shipping on 2026-07-26: four ITV boards self-healed their bottles because an unrelated estate-audit sibling happened to write them, and its commits pushed the healing to the org — it carried the fix without knowing. **The boundary, and it is real:** a repo that gitignores `.bon/` is healed **locally only** — the write succeeds, the sync silently doesn't. So a ride-the-write design converges the estate *minus exactly the kizeje class* (bon-kizeje), and any future mechanism of this shape should name that exclusion in its own brief rather than rediscover it in production. Dormant boards — never written — need the deliberate route (`bon doctor --fix`), which is why the doctor half shipped alongside the automatic half rather than after it.

**Legibility over abstraction.** No base classes, no registries. Each command is a self-contained function with the same boilerplate at the top. The repetition is deliberate.

**LLM-ergonomic first.** `--quiet` for agents to capture just the ID. `--json` for piping. `--parent` aliased to `--outcome` because Claude's training priors are stronger on `--parent`. `check_outcome_language()` coaches agents away from activity framing. **Skill prose cannot override Claude's procedural priors** — four iterations of increasingly forceful skill guidance failed to make test Claudes pipe JSON to `bon new` instead of using flags. The fix was making JSON-from-stdin the CLI default (change the tool, not the instructions). This principle applies broadly: when the "right" invocation differs from what Claude learned in training, change the CLI's default behavior rather than fighting the prior with documentation.

**The caller-mistake ladder is contract (bon-siciri, adjudicated 2026-08-16 — the doctrinal statement lives in docs/CONTRACT.md).** When a calling model's priors misfire, a verb absorbs silently (never — the forgiving harness is the training mechanism behind slop, per Ronacher), refuses loudly naming the right move (the floor; measured estate-wide, 76% of errors clear on the next call), coaches, or bends to the prior *with the repair reported in the tool result* (silent bending is absorption by another route). Evidence picks the rung: a stable wrong grammar means bend, a zoo of mistakes means refuse better, and a mistake producing no error at all needs an announcement — which is instrumentation, since errorless mistakes are invisible to transcript mining. The siciri verdicts applied it: verb-noun grammar declined with a tripwire (revisit if invocation logging shows it as a stable high-frequency miss — erg-vikoke will make it countable); `--append-how` shipped (the RMW workaround was the hazard); `bon new` announces its species; `convert --outcome none` bends to the spelling `edit` itself taught. Triangulated against `~/notes/practices/tool-ergonomics/` (brief + 300,637-call diagnostic; bon measured healthiest high-volume CLI at 3.7%).

**Sample real instances before designing.** When proposing a CLI improvement from a usage audit, the headline statistic names *candidates*; the raw right-side-of-pipe expressions reveal what users were *actually* trying to do. The `bon-wofuwu` audit (2026-04-29) said "173 status-extraction expressions in pipes vs 13 `--status` flag uses" — sounded like `--status` was the missing verb. Two minutes reading 20 actual pipe expressions revealed the dominant pattern was `head -N` truncation (~110 cases) and that 25 apparent "missing pretty-print" cases were redundant — `bon show --json` already pretty-prints. `--limit N` shipped because evidence pointed there, not the louder `--status`. The regenerable recipe (find ~/.claude/projects + grep tool_use Bash for the CLI in question) is shape-portable across any CLI; what makes it land is the second pass of reading what people typed before designing what they "should" want.

**Briefs are a forcing function.** `{why, how, what, done}` forces clear thinking. `how` is optional — captures approach/strategy/constraints when the work is complex enough to need it. Numbered items in `what` become extractable tactical steps, making the brief executable. `bon work` surfaces `how` as "Approach:" context above the step list. A bon brief with all four fields replaces a plan file — the plan IS the bon hierarchy. The fifth field, `badly`, is the one a Claude must *not* fill (see "The falsifier" above).

**The Calvino principle.** In Calvino's *If on a winter's night a traveller*, the chapter titles read as a continuous story — the Table of Contents IS a narrative. Bon outcomes work the same way: read them in sequence, they should tell the implementation story. Each title is a clause in the project's journey. Each outcome expands into actions with rich `--how`. The narrative lives in the sequence; the detail lives in the chapters. This principle, implemented as the `/plan` skill, eliminates the plan→bon transcription problem entirely: understanding.md provides the architectural frame (maintained by /open and /close), the Table of Outcomes provides the narrative, and actions with `--how` provide the execution detail. No separate plan document. No transcription step. No fidelity loss.

**The `--what` gravity well.** `--what` attracts all content — implementation detail, constraints, approach — because it's required (so you're already composing there), semantically broad ("what will we produce" blurs with "how will we build it"), and `--how` is optional with no CLI nudge for its absence. The result: `--what` carries both deliverable and implementation detail, making briefs hard to scan. The fix on the authoring side is deliberate redistribution: `--what` for the deliverable, `--how` for the implementation approach, constraints, and pitfalls. Some plan content still has no natural bon field: cross-action dependencies (bon has ordering but no explicit dependency tracking), verification procedures (distinct from `--done` criteria), and cross-cutting architecture notes. These get embedded as conventions within `--how` (e.g., "PITFALLS:" prefix), which works but isn't structured.

**Dispatch, not hierarchy.** The Dolt backend was added without class hierarchies or strategy patterns. Six `if _get_backend() == "dolt"` branches at function boundaries. Simple, readable, easy to remove if the experiment fails. (Its write strategy was truncate-and-reinsert "to keep both backends' concurrency guarantees identical" until 2026-08-23 — that parity was measured illusory and the strategy is now item-grain diff-at-save; see the Atomic-writes invariant above for the full story.)

## The orchestration-wave pattern (bon-turibi — measured 2026-08-17; codified and closed 2026-08-23 in aboyeur `docs/wave-pattern.md`)

Unattended executors do the work well and misreport it slightly: small, confident overstatements in their summaries (four of four wave-1 items; an explicit precision-audit instruction in the dispatch brief cut that to one of four in wave 2). Adversarial verification — a sceptic per item — ran about a third of total spend and caught every drift; it is the honesty layer, never optional, because without it those inflations enter the record verbatim. Dispatch briefs written to disk *before* launch give verifiers an independent spec (checking an executor against its own narrative only proves self-agreement) and enable mid-run fact injection — used live when a sibling lane's attribution facts arrived while an executor was still running. Constraints phrased by mechanism ("notes-sync owns git *writes*"; "deletion is irreversible, disabled is the reversible rung") leave no letter/spirit edge for a reasoning agent to slip through, where bare prohibitions get benignly reasoned around.

The board-facing consequences connect to standing concerns. Boards move under fleets, so freshness-gate every dispatch — a gate turned a mid-wave collision (an item closed and re-homed under the wave) into a recorded divergence rather than a corruption (the lezole family, seen from the dispatcher's side). Log dropped items explicitly rather than filtering them silently, and expect retry chains to leave half-written worlds the surviving attempt must discover and absorb. And the no-board-writes discipline that keeps waves safe also makes their claims invisible: a line living in both a wave brief and the standing dispatch queue is double-drawable — bon-hunote's design question (hunote is parked until aby-degeki ships its dispatcher role).

The 2026-08-23 codification settled the doctrine's shape: the measured record, dispatch-brief template, COMMON.md verbatim and the when-to-wave-vs-loop test live in aboyeur `docs/wave-pattern.md`; the worked briefs were rescued from scratch into the private notes room before the ephemeral pointer rotted. The wave keeps a named niche — parallel *read* work, because parallelism belongs where writes don't — while sequential loops carry write work. The verification half generalised into loop doctrine as the **per-verdict cold-eyes sceptic** (aboyeur loop.md step 4, born from the wave pilot's 4-of-4 overstatement measurement): a fresh context checks each verdict at the moment it's written, at roughly a third of spend. It caught real drift twice on its first day — turibi's own close was missing an uncommitted template hunk, and resena's sceptic forced publish-before-close. The failure it guards, confident self-agreement at the moment of writing a verdict, is invisible to the author by construction — which is why the check cannot be an instruction to try harder and must be a fresh context.

## The skills layer

Bon ships three Claude Code skills plus a session-start hook. `/open` handles session orientation — synthesizing knowledge from the previous handoff's "For Claudes to come" zone into understanding.md, draw-down/draw-up discipline, and the plan-to-bon transmutation. `/close` handles end-of-session reflection and produces a two-zone handoff: "For the next Claude" (operational context — done, risks, opportunities) and "For Claudes to come" (durable knowledge for understanding.md synthesis). `/review` orchestrates periodic backlog review. `open-context.sh` is the hook that provides mechanical context (understanding, handoff, outcomes) before the LLM-mediated `/open` ritual kicks in.

**/review surveys the whole estate; verification stays local (1.5.0, bon-hobufa/mewufa).** `audit_survey.py` is hybrid: a Dolt-global query is primary (labelled via the `repos` table; first real run 2026-07-08: 491 open items across 27 boards, 169 of them invisible to the old filesystem-only survey), plus a JSONL straggler sweep for filesystem boards. Items whose repo has no clone under the scan roots classify **NOT_VERIFIABLE_HERE** (naming which machine/clone could verify) — they never degrade into trust-the-brief, and closing them needs a clone or an explicit deferral because the bon CLI is board-scoped by cwd. `not_cloned_here` means "no clone under the scan roots", not "not on this machine" — `~/.dotfiles` is the standing exception (Dolt-backed, outside roots, actually local). A Dolt outage degrades the survey to JSONL-boards-only — local Dolt boards *also* read empty, since `bon list` needs the same server — so the fallback names itself loudly rather than posing as the whole estate. Orphan prefixes with no living clone surface fail-visible for triage in the review venue — don't "clean them up" outside it. The known backlog (consomme, day, gm, tmig, arc, sl, work) was **fully closed 2026-07-08** via loguvu's orphan-close recipe (scratch reconnect → real `bon done`/`archive` → committed `DELETE` of the scratch `repos` rows; recipe in the review SKILL.md Phase 4); the mechanism stands for future orphans, with `bon --board <prefix>` (bon-wezahu) as the deferred permanent fix.

**A review has two orthogonal axes, and only one scales (2026-07-08, first 650-item run).** Subagents verify **TRUTH** — does the brief still match the code — and do it superbly at 30-parallel scale (evidence notes, premise-vs-remedy discipline, kegewe open-children awareness; three independent agents caught the kegewe trap). **DESIRE** — does the human still want the thing — cannot be inferred from any substrate: a git-quiet repo reads identically as "finished, in daily use" and "abandoned" (the ecoute lesson, re-proven when signboard read as moribund but was *newly dead and wanted back*). Desire triages at **REPO/OUTCOME level, not item level** — presenting 145 item verdicts drowned the user ("I'm drowning"); six repo-level questions then resolved the whole doubt zone in one exchange. Run reviews as: survey → verify truth mechanically → present the portfolio grouped by pulse → ask the desire questions only the human can answer → only *then* touch items. Vocabulary that worked: **VEIL** (close with a recorded no-regrets note + reopening condition — an examined no-action, not done-work), **FOLD** (merge into a living sibling), **CONVERT** (`bon convert` demotes a task-shaped "promise" to an action — honest shrinkage without losing the work). And the decision-by-veil tell: ten weeks of nobody running a well-designed PoC *is* the PoC result — a veil with a tripwire beats evidence-gathering nobody will do (the ADK no-go, plg-pazahi).

**Operational lore for the next big run (bon-loguvu's fixes shipped in suite 1.5.1, 2026-07-08).** The headline count moves with **clone availability** (491→650 overnight purely from tube gaining JSONL clones) — the survey now emits `visibility_note` + `dolt_open`/`jsonl_open` so a jump reads as clones appearing, not work. `item_record` now passes `how` through (was silently dropped: 0/650 on the first run) and derives `open_child_count` on outcomes, so the kegewe open-children trap is visible in the data, not just caught by the `bon done` warning (parent/waiting_for always flowed — the first-run handoff's "strips parent/waiting_for" was imprecise; only `how` was missing). The SKILL.md now carries an **EXTERNAL_SURFACE** class (done-criteria on Drive/Confluence/SaaS, distinct from UNCLEAR), **rolling dispatch** (refill slots on completion, not strict waves), a **TRUTH/DESIRE Phase 3** (verify truth mechanically, but hold the desire conversation at repo/outcome level *before* item tables for big estates), and an **orphan-close recipe** (scratch reconnect + real `bon done`/`archive`, then a committed `DELETE` of the scratch `repos` rows). The prefix-squat backlog is **cleared** (bon-kafono, 2026-08-16): cornichon went to `crn-` (2026-08-08), carnet to `carnet-` sometime before, and the last two were re-prefixed in place — piano → `piano-` (16 done items), mit-agentic-sales → `mas-` (14 items, Rupert's board, understanding.md citations updated, handoffs left as records with a `.bon/id-migration-2026-08-16.md` bridge). The survey now emits `duplicate_prefixes` (two layers: local boards grouped by prefix with same-origin clones exempt, plus JSONL boards squatting on a Dolt-registered prefix — so the owner needn't be cloned locally); still never map prefix→repo with a dict comprehension that lets last-writer win. The `bon --board <prefix>` flag that would retire the scratch-reconnect dance stays filed with a tripwire (**bon-wezahu**), not built.

**A review's yield is repricing, not closure — measured 2026-08-08 (the big-five truth pass, bon-zamece).** 243 items verified against code across the five biggest boards (cornichon 73, bon 53, carte 47, plongeur 38, mise 32): 5 DONE, 3 STALE, 12 BLOCKED — and 172 of 243 (71%) repriced. The mechanism: a brief is written at the moment of *least* knowledge about the work, and everything that happens afterwards — siblings shipping, blockers clearing, premises dying — makes it wronger in one direction. **Briefs rot toward pessimism**: they say pending when it shipped, blocked when the gate opened, five steps when it is one. An overstated remaining cost actively deters its own completion, so the rot is a compounding tax on everything unfinished. The rite currently discards this yield *on purpose*: `skills/review/SKILL.md:342` ("Audit is triage, not rework") and `:369` (brief-editing listed as an anti-pattern) were a sensible scope decision made under the assumption that audits mostly close things — an assumption now measured wrong by more than an order of magnitude. bon-zewake carries the revisit, framed as a scope decision to re-make with evidence, not a feature gap. Open beneath it: whether append-only dated CORRECTIONs scale — right at ~10 per run, brief-bloating at 172 per cycle. Dispatch lore from the same run: **chunk verifiers by outcome subtree, not per item** — sibling state is evidence (one verifier saw an outcome's remainder was two items not five, because three siblings had closed); and adding a `repricing` field to the verdict rubric was the single highest-value rubric change.

**Hook output should front-load what's different, not what's true.** Dynamic content (handoffs, tactical state, recent changes) belongs first in hook output — stable reference (architecture, data model) belongs in explicit Read steps triggered by skill instructions. Truncation kills the tail, and dynamic content has no other delivery path. The principle: hook output decays, skill-driven reads persist. This was validated when understanding.md (~7KB) was output before the handoff, pushing "For Claudes to come" past the 2KB truncation point — the knowledge pipeline silently stopped flowing until the ordering was fixed.

**Refined 2026-07-28 (bon-peluge): the axis is not dynamic-vs-stable, it is *bounded and orphaned* vs *unbounded and addressable*.** The rule above put the handoff first because it is dynamic — and that is what then spent the entire ~2KB preview budget on the handoff's Done bullets, pushing `UNDERSTANDING=`, the item list and the Suggested picks past the cut (observed on spm1001/passe 2026-07-21 at 10.4KB; sighted again 2026-07-27 in an unrelated session that had to go read the persisted file to find "For Claudes to come"). But the handoff body is *not* orphaned — it is a file on disk. Once the hook prints `HANDOFF=<path>`, the body becomes the safest thing to truncate, because a cut there is recoverable by one Read. So the ordering rule is now: **anything short, curated and with no other delivery path goes first; anything unbounded goes last, with its address stated up front.** Concretely `open-context.sh` emits greeting → last-session line + `HANDOFF=` → `UNDERSTANDING=` → Suggested → outcomes → standalone → active work → contributions → handoff body.

Two things that fix taught, both worth keeping. **Reordering alone was not enough** — a 16-item standalone pile still pushed Suggested past the cut, so any section that grows with the board needs an actual cap (`STANDALONE_MAX=12`), and the reorder-only version would have passed a synthetic test while failing the real board. Assert the budget against the *real* emission, not a fixture. And **a cap must state its remainder** (`… +N more — full list: bon list`): a silently truncated list reads as completeness, which is a worse failure than a long list — the same "no silent caps" discipline the review skill applies to coverage.

**The baton outranks the item lists.** The baton — the outgoing Claude's pointers — is small, bounded, and the highest-value-per-byte content in the briefing; the full landscape is large, growing, and available on demand from `bon list`. When budget is scarce, hand over the baton before describing the field. (The hook section was relabelled 2026-08-02 from "Suggested:" to "From the last handoff's Opportunities:" — bon-dokahi: the old label vouched for content whose register had drifted.)

**Three temporal rhythms govern the session lifecycle.** Rapid-cycle (~30 /close+/open pairs per day) carries operational context via Gotchas/Next in the handoff's "For the next Claude" zone. Overnight composting carries durable insight — Learned sections flow into understanding.md (the Done→garde-manger extraction leg was retired when garde was decommissioned 2026-06-03). Anthropic's background system (autoDream) consolidates MEMORY.md from session transcripts, carrying typed observations (feedback/project/reference). The handoff's two-zone structure maps directly to the first two rhythms. We don't need to write to MEMORY.md explicitly — a rich handoff in the session transcript feeds Anthropic's system naturally.

**A rite change's proof is its next natural execution (2026-08-09).** Skill text is session-cached, so nothing in the session that ships a rite change can exhibit it — "prove it next session" is structural, not a compromise, and the pattern banked three proofs in one day: jagoha was proven by the ceremony running it, zewake by its 16 corrections surfacing at the gate it built, and leturo parked its tactical *at the proof step* (released at 5 of 5) so the next /open resumes straight into it. Two companion disciplines: when the human utters a norm mid-conversation ("I'd like you to tell me, but doing it is fine"), record it verbatim in the item's `--how` at that moment — an hour later it was quotable inside the shipped skill, authority intact. And when a norm changes mid-day, sweep the briefs written earlier the same day under the old norm: leturo's own `--done` ("nothing ever writes to Todoist") contradicted its updated `--how` within the hour, written by the same hand.

**Skill gates shape Claude behavior at critical moments.** The /close skill's Reflect phase gates what goes into bon vs handoff prose. A previous gate ("if this never gets done, what breaks?") biased Claudes toward deferring actionable work into handoff text. In a real 12-hour mind-sweep, this produced 6 outcomes with zero actions — the entire breakdown step was skipped. The fix: bon is the default for anything specific enough to write `--why`/`--what`/`--done`. "Handoff only" is restricted to genuinely non-actionable context (open questions, taste judgments, architectural tensions). The lesson: gate questions in skills are load-bearing. A permissive gate at close time compounds — work that should be tracked disappears into prose that no future Claude will parse.

**Scripts live in `scripts/`, skills in `skills/*/`.** Both ship in the plugin cache. Path resolution must exclude `skills/*/scripts/` when searching for top-level scripts — `find -path "*/bon/*/scripts"` matches both because `*` spans `/` in `-path`.

**`~/.claude/rules/*.md` auto-loads into every session.** Confirmed by test (magic-word shard). This means plugins can own instruction shards without `@include` wiring in the global CLAUDE.md. The pattern: a plugin's SessionStart hook symlinks its `instructions.md` into `~/.claude/rules/<plugin>.md`, using BASH_SOURCE-relative resolution so version updates auto-propagate. The `~/.claude/` write restriction only applies to Claude's tool use (Write/Edit), not to subprocess hooks — so hook scripts can create symlinks without permission prompts.

**Instruction shards separate always-on rules from skill context.** Shards in `~/.claude/rules/` carry only gates and overrides (e.g. "use bon not TodoWrite", "passe fetch not WebFetch"). Full instructions live in SKILL.md and load when the skill is invoked — no duplication. The `@context/` include mechanism and `rules/` auto-load are complementary: `@context` is hand-curated composition controlled by CLAUDE.md, `rules/` is plugin-managed auto-load controlled by directory contents.

**Rules files support path-scoping via YAML frontmatter.** Without frontmatter, rules are unconditional (always loaded). With a `paths:` field, rules only activate when Claude is working on files matching those glob patterns. Syntax: `---\npaths:\n  - "src/**"\n---`. Batterie instruction shards are unconditional (behavioral overrides apply everywhere), but path-scoped rules are available for file-type-specific instructions.

## Plugin resolution gotchas

**Claude Code resolves plugin skills by directory name, not the SKILL.md `name:` field.** Renaming the `name:` without renaming the directory means the old invocation path stays active and the new one never registers. Similarly, hook scripts in `hooks/` are inert unless registered in `plugin.json` under the `"hooks"` key — the runtime doesn't scan directories. Both are silent failures: no error, just nothing happens. A version bump is required after fixing either, because `claude plugin update` compares versions, not content — same version means "already up to date" even if files changed.

**The publish pipeline changed underneath this repo on 2026-06-10 — pushing is no longer publishing.** `spm1001/batterie` (no `-de-savoir`) is the single marketplace; it *vendors* plugins inside itself. The recipe: push source → `gh workflow run "Assemble plugins" -R spm1001/batterie` (drift-guarded bot vendors all source repos from their GitHub HEADs) → `claude plugin marketplace update batterie` → `claude plugin update bon@batterie` → CLI reinstall (`uv tool install ~/repos/spm1001/bon --force --reinstall --no-cache --with pymysql` — `--no-cache` is load-bearing, not optional: a plugin.json-only bump leaves `src/` byte-identical, so without it uv reuses the cached wheel and the version never moves; `uv cache clean bon` does *not* clear that build — bon-babuse, 2026-06-17) → full session restart. Version coherence has exactly two points: source `.claude-plugin/plugin.json` and the bot-vendored copy; the marketplace entry pins nothing. The version must change or `update` reports "already up to date" even when files differ. Reloading plugins mid-session doesn't trigger SessionStart hooks or refresh already-loaded SKILL.md content. Every step is a potential silent failure point.

The canonical silent failure already happened: the assembler's lean copy-list omitted top-level `scripts/`, so the cutover's first publishes (0.24.0, 0.25.0) shipped without close-context.sh/open-context.sh — `/close` dead-ended and the session-start hook silently degraded. Fixed structurally in batterie `4ce575f` (2026-06-11): `scripts/` in the copy-list, parity guard on both branches (source ships a capability dir but the vendored copy doesn't → hard FAIL). Residual hazard: machines update independently — hezza being current says nothing about the Mac, which sat on scripts-less 0.25.0 for a day after hezza was healed (bon-fivemu, 2026-06-12). When a "fixed" plugin bug recurs, ask *which machine's cache* before re-diagnosing.

**What the assembler vendors, and how the ratchet works (2026-06-17 — verified against `assemble.sh`).** Skill plugins (bon — no `mcpServers`) are vendored via the *lean copy-list*: `commands skills agents hooks scripts .mcp.json CLAUDE.md instructions.md` plus `.claude-plugin/`. **`docs/` is NOT in it** — and the full-source (MCP) branch `--exclude /docs` too — so bon's `docs/` never ships to users. The *version ratchet* runs `git status --porcelain -- plugins/$plugin` on the **rsynced output** (excluding `plugin.json`) and fails the build when content changed while the version didn't. Two things future Claudes keep getting wrong: (1) **a `docs/`-only commit cannot trip the ratchet** (docs aren't vendored) — so don't diagnose a ratchet failure as "the docs drifted"; it's a change to a *vendored* file (CLAUDE.md / a skill / a hook / instructions.md) shipped without a `plugin.json` bump. (2) The ratchet **quarantines** a laggard rather than blanket-aborting (bds-pujaki, shipped 2026-06-17): it reverts that plugin's vendored dir to its last-published version, lets the healthy plugins still ship, then fails the run red naming the laggard — so one repo's missed bump no longer wedges the whole bus. (The assemble cron still has no failure alerting, so a red run can sit unnoticed.) Worked example: 2026-06-17 a one-line CLAUDE.md edit (the `docs/CONTRACT.md` Key Files pointer, shipped at 0.26.2 without a bump) tripped it and blocked every plugin for ~4 days — and the wrong "docs drifted" story reached three artifacts before the copy-list + publish-diff settled it (0.26.3 cleared it).

**The briefing's Opportunities section ("From the last handoff's Opportunities:") is a baton pass, not a board view.** It pulls from the previous handoff's Opportunities (fond-v1) or Next items (legacy) — the outgoing Claude's pointers — not from `bon list --ready`. The full ready list is available on demand, but the startup stream carries only what the last Claude recommended. Bon IDs appear naturally when the outgoing Claude referenced them in handoff Opportunities, giving the incoming Claude a direct `bon work` handle. This is Claude-to-Claude communication; human readability is secondary. When the baton is in context from the hook, don't re-run `bon list` to pick direction — it's redundant and burns tokens. `bon list` is for the full picture: hierarchy, status, mid-session transitions, or auditing completeness. Since 2026-08-02 (bon-bafume) the section carries four truth guards: the label names its source instead of vouching for it (dokahi), bullets naming only closed this-board items are dropped with the omission stated (mosase), each bullet trims to its first sentence under a count cap with remainder stated (wokapu), and the "Last session" age derives from the handoff's header date, not clone-flattened mtime (wakaju). Writers: lead each Opportunities bullet with the point — only the first sentence previews.

**A session-ritual hook must never be the thing that breaks orientation — treat cross-tool input as untrusted (2026-07-14, the `xhigh` crash).** The session-start dashboard (`session-dashboard.sh`) shows a context-window gauge whose denominator it reads from `/tmp/.claude-ctx-{pid}`, a sidecar written by a *different* tool (the statusline) on a filesystem convention neither side's contract documents. A statusline bug — `IFS=$'\t'` + jq `@tsv`, where tab is IFS *whitespace* so `read` collapses consecutive tabs and any empty field (null `context_window_size` on early turns, no `output_style`, no rate-limits on Vertex) shifts every later field left — leaked the effort level (`xhigh`) into the window slot and thence the sidecar. The dashboard then did `$(( xhigh / 1000 ))` and died under `set -u`. The fix (shipped suite 1.9.1): the dashboard now **validates the sidecar is numeric and falls back to model-inference otherwise** (keeping the window *correct*, not just non-crashing), plus a belt-and-braces coercion. The principle: when a hook consumes another tool's output across an undocumented boundary, validate its shape and degrade gracefully — never crash on it — because the writer carries fragility classes the reader can't see. This bites *hardest* in a session-ritual hook, whose entire job is to make orientation reliable: defensiveness at that boundary is not optional. **Cousin craft lesson (byte contracts):** the statusline fix switched to the `\x1f` unit-separator (non-whitespace → empties preserved); getting the delimiter right meant `od`/`cat -A` on the *emitted bytes*, not reasoning through the JSON→jq→shell escape stack (the Edit tool's JSON layer collapsed the separator to a raw byte that read as `join("")` in source; a double-backslash mismatch broke a sibling copy — both caught only by hexdump). When a byte or delimiter is load-bearing, verify the file's actual bytes and leave an in-file comment marking the non-obvious choice as spec ("Do NOT revert to @tsv/tab") so a future maintainer doesn't "simplify" it back into the bug.

**The hook's own pipeline discipline is the other way orientation dies — under `set -euo pipefail`, a bare `grep` that matches nothing IS a death sentence (bon-cuvice, 2026-07-21).** open-context.sh section 3's `grep '^○'` exited 1 on outcome-less boards and killed the hook mid-section — the "bare/dying header" symptom was the script *dying*, not a filter quietly returning empty. The pattern that survives: capture with `VAR=$(... | grep ... || true)`, then emit headers only when the variable is non-empty (outcomes and standalone now filter separately). Same family as the xhigh sidecar lesson above — a session-ritual hook must never be the thing that breaks orientation — but where that one was untrusted *cross-tool* input, this killer was the hook's own pipeline. Fixed in suite 1.17.0 with 5 red-then-green tests; verified live against passe's standalone-only board.

**The ensure-*.sh hook family has two shapes — and shared a latent JSON bug.** The batterie SessionStart hooks split into **CLI-installers** (bon/passe/todoist: `uv tool install "$INSTALL_SRC" --no-cache`, where `$INSTALL_SRC` is the local working tree when it has a `pyproject.toml`, else `<pkg> @ git+https://…` — the vendored marketplace plugin ships no `pyproject.toml`, so post-cutover *every* install resolves to git+https) and **MCP-server ensurers** (tafelmusik/mise: `uv sync` into a plugin-root `.venv`, no CLI). The babuse `--no-cache` lesson applies only to the former — a plugin.json-only bump leaves `src/` byte-identical, so uv reuses the cached build and the version never moves (this also bites `uv run bon` in the dev tree: hatchling bakes the version from plugin.json at build time, so refresh with `uv sync --reinstall-package bon --extra dolt --no-cache`). The shared bug, fixed across all four 2026-06-20 (bon-mavemi/bon-dotupu): a hook rendering output via raw `cat <<EOF` interpolation emits **invalid JSON on its failure branch** whenever a message carries an interpolated quote — `\"$INSTALL_SRC\"` / `\"$PLUGIN_ROOT\"` in a recovery command closes the JSON string early. It hides from every success-path test (the quotes appear only in failure messages) and `bash -n` can't see it; the only check that catches it is a *forced-failure* render piped to `python3 -m json.tool`. Fix: render via `python3 -c "…json.dumps…"` (bon's pattern from the start), never a heredoc. tafelmusik's render is still inconsistent (JSON on success, plain text on the systemd fallback) — bon-dotupu.
