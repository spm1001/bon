### Reflection
- **Build the red before the green, and build it out of the real thing.** A synthetic external-consumer fixture — a bon board with two handoffs in `.bon/handoffs/`, no visible dir, run through the actual `open-context.sh` — emitted no `HANDOFF=` line at all with the rung retired and no migration, while both files sat intact on disk. That transcript, not a unit test, is what forced the migration into the READ path. The tidier reading of the precedent in `storage.py` — where the bottle, `.bon/README.md`, gets refreshed parasitically on every save — would have put the migration only in `/close`, and a consumer whose next contact was an open would still have lost their history.
- **The adversarial verifier earned its keep.** That is a cold review session, given the diff and one axis to attack, told to refute rather than agree. It found a BLOCKER I would otherwise have shipped: when `handoffs` and `.bon/handoffs` are the same physical directory — a symlink shim, the obvious way a consumer adopts the visible convention without rewriting git history — the dedup branch compared every file to itself, called it an already-migrated duplicate, and `rm -f`'d the only inode. It was silent, too: count 0, no message, exit 0, and permanent on a gitignored pile. Every collision test I had written used a real copy, so the suite green-lit the branch. Two names can reach one inode, and only `-ef` checks for that.
- **Known-bad controls, twice — and the second pass caught a vacuous test.** The first control, an early `return 0`, turned 9 of 11 migration tests red. After the verifier's fixes a second control showed my new hardlink test passing *without* the guard it was meant to be testing, because unlinking one of two links leaves the content readable, so the assertion could never fail. Asserting on the legacy path instead made it discriminate. A test written to pin a fix is worth exactly as much as its failing run.
- **A pre-existing latent bug becomes yours when your change mints the state that triggers it.** `find_latest_in` ended with `[ -n "$best_file" ] && echo`, which as a function's last command returns 1 on an empty directory and kills the script under `set -euo pipefail` before any output — with `session-start.sh`'s `|| true` swallowing it into a completely silent no-briefing session. It had been there all along, but the migration's failure path creates the destination before attempting each move, so it can now mint the empty directory that fires it. That is fixed here. `lib-handoff.sh`'s own header bans the idiom; the bug lived in the neighbouring file.

## For Claudes to come

**Retiring a read path from a tool that ships publicly is two changes, and shipping only the first is the failure.** "Our machines are migrated" is a different claim from "every consumer is migrated" — bon reaches MIT teammates and family machines through the batterie marketplace, and their repo state is not observable from here. So removing the old path and converging the people still on it have to land in the same version, with the convergence running before any read, at every entry point. Otherwise there exists a session where their history is simply absent and nothing says why.

The instrument that generalises is the **synthetic consumer fixture**: build the state you are about to break — the real repo shape, run through the real entry-point script, not a unit fixture — and watch it fail first. A migration tested only after the fact proves the migration works. It never shows you what the un-migrated consumer would have seen. Here that view was a briefing with no "Last session" line sitting above two perfectly intact files on disk.

And the lesson that cost a BLOCKER: **a migration's dangerous branch is the one that deletes, and a deletion must key on physical identity rather than on names or contents.** "The target exists and compares identical, so this is an already-migrated duplicate — drop it" is sound reasoning, right up until the two paths reach one inode, when the same branch deletes the only copy. Whenever code decides that two paths hold "the same" file and one can go, ask what happens if they *are* the same file; `-ef` answers it in a single test and no amount of content comparison ever will. This survived review because every test used a copy, which is both the natural fixture to write and the one shape that cannot expose the bug — so if you are reviewing a deduplicator, the absence of a symlink test tells you nothing has checked the case that loses data.
