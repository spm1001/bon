## For Claudes to come

**On a shared substrate written by mixed tool versions, model a new orthogonal fact as a field, never as a status-enum value — and more generally, choose the failure mode you can watch.** The two options fail in opposite directions: a new enum value makes items *invisible* to every old reader filtering on the enum (`status == "open"` is everywhere — CLI, hooks, raw jq, the survey), which presents as silent deletion on any not-yet-updated machine; a new field merely *decays* when an old writer's fixed column list rewrites the row, and the item stays visible the whole time. Bon's Someday/Maybe shipped as a `someday` field on this argument (2026-08-02, status stays open/done — same grammar as `waiting_for`, which was also deliberately not a status), and the estate proved the reasoning within the hour: a parallel session running the previous CLI nulled a fresh park 57 seconds after it landed, the item never vanished, the fingerprint was legible (`updated_by` survived; the unknown column didn't), and the fix was a publish — because the CLI is a per-command subprocess, even already-running sessions converged on their next call. The corollary from the same evening's sweep: state kept in *title prefixes* rots in both directions — five "Someday:" items were parked-in-spirit with no revisit condition anywhere, and one had been formally promoted to active months earlier while its title still wore the parked costume. A fact worth keeping is worth a field the tools enforce; a fact kept in prose decorations will eventually contradict the record, silently, both ways.
